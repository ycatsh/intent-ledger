{% endmacro %} {% block content %} {% call modal("rules-info-modal", "How rules, transfers, and overrides work") %}

Every transaction needs a category. Rules, transfers, and overrides are checked first; if none of them apply, it falls back to the payee's default account, and only lands in Unknown if there's no default either. These three tabs are the ways a category gets picked automatically, in the order they take effect.

  • Rules match a transaction's description (contains, prefix, suffix, exact, or regex) to a category. Rules are checked in priority order, and the first match wins. A rule beats a payee's own default category. A rule can also optionally name a payee - useful for a recurring charge with no fixed default - which only fills in a transaction that doesn't already have one; an alias match or a manual assignment always wins over it.
  • Transfers use the same kind of pattern match to flag transfer candidates, then pair them up with a min-cost match (the Hungarian algorithm) that weighs date and description similarity, so a transfer between your own accounts never shows up as income or an expense. A candidate that doesn't find a pair is categorized like any other transaction.
  • Overrides set the category for one specific transaction by hand, from the Accounts view. An override always wins over a rule or payee default, and a split always wins over an override.
  • Splits divide one transaction across as many categories as you need. The editor tracks how much is still unassigned, and the split only saves once the lines add up to the full amount.
